# 入水水花：叠帧与原作节奏调查（2026-10-20）

## 结论

用户指出的“相邻水花叠在一起”与当前代码一致。当前运行时每次刷新同时采样相邻两张水花贴图，对预乘颜色和透明度做交叉淡化。这会让两套不同位置的水滴、泡沫和水柱在换帧中途同时可见；它没有生成沿运动路径前进的新形态。

原作现有连续录像支持另一种做法：保持一张水花形态，随后切换下一张，没有观察到当前这种跨整张水花的连续交叉淡化。原作贴图本身已有不同明度、半透明的水层，这些空间层次不能误判为跨时间叠帧。

“画面渲染刷新率”和“水花绘画形态更新率”应分别讨论。现有录像中的水花并不是每个 60 Hz 采样帧都换一张形态；不能再用双帧淡化冒充提高水花形态帧率。

## 证据一：当前实现

- `mod/src/Vfx/DiveFx.cs`：`SplashStep = 0.053f`，即约 18.87 次形态切换/秒。
- `Tick()` 计算 `si = floor(t / SplashStep)` 和小数部分 `frac`，绑定 `si`、`si+1` 两张贴图，把 `frac` 送给 `frame_mix`。
- `mod/src/Vfx/Shaders.cs` 的 `PileSplash`：两张图先预乘 alpha，再执行 `mix(a, b, frame_mix)`。
- 当前实现已是单次绘制中的预乘混合，避免了旧式两层透明绘制造成的覆盖率下降。但这只纠正混合算术，仍然保留了两套轮廓交叠的问题。
- 以 50% 为例，图 A 有水滴、图 B 对应位置没有水滴时，旧位置留下半透明水滴；与此同时新位置出现图 B 的半透明水滴。水滴没有移动到中点，画面同时有两个位置。

`水花_单帧与交叉融合对照.png` 左右是原始素材 02、03，中间严格按当前着色器的预乘混合计算 50% 状态。下排放大同一块区域。中间可直接看到两组轮廓。

### 辅助轮廓拟合

对第 20～42 帧逐帧取亮青水花轮廓，比较单张素材与相邻两张素材线性混合：
- 23 个样本的最佳混合权重均贴近单帧端点，另一张贡献不超过约 2.4%。
- 允许相邻混合后，相对单张拟合的误差改善最多约 1.8%，没有显示出 25%、50%、75% 的连续淡化过程。
- 此统计存在录像压缩、贴图缩放、背景颜色、遮挡和阈值误差，因此作为目视连续帧的辅助证据，不将误差里的少量权重当成原作真实混合参数。

## 原作“流畅”的可验证部分

已经提取的资料确认该画面是多种动画层合成：
1. 水花使用有明确形态设计的序列贴图；所查录像中按节奏换形态，轮廓保持干净。
2. 主角是带骨骼动作的实时 3D 模型，并非同一张立绘随水花换帧。
3. 水面有独立 UIM 网格动画：In 为 75 帧、Loop_L 为 210 帧，此外有独立焦散/水光资源。

因此水花形态可以保持几帧，同时人物和水面仍在运动。整体流畅不能归功于混合相邻两张水花。关于原作内部采用哪一种骨骼、网格插值及具体每层刷新率，目前没有完整运行时代码，不能仅靠导出文件作出确定结论。

我们的骨骼位置/旋转插值和 GPU 水面位移插值，均是在更新同一个物体的姿态或取样位置，与把两张不同形态的水花同时显示有本质区别。前两项可以保留。

## 建议的修正

1. 水花改为同一时刻只显示当前一张，移除两张水花颜色/alpha 的交叉淡化；保留原贴图自身的透明层次。
2. 以这份原作样本的约 1/15 秒作为校准候选节奏，与人物入水、水下露出和最后消散一起预览；不能只降低换帧速度而忽略整段时间轴。
3. 末尾如果需要淡出，只衰减当前一张水花；不要靠下一张叠进来淡出。
4. 继续使用真实时间选择当前帧，卡顿后跳到应有进度，不排队补播过期水花。
5. 保留已有资源预热、GPU 波浪缓存、骨骼插值、In→Loop 连续衔接。这些性能修复不要求水花双帧融合。
6. 水下露出遮罩、焦散和水花分开验收，避免为了水花“顺滑”又额外叠两套可见轮廓。将实际游戏的画面刷新率与水花形态更新率分别记录。

去掉第二张可见水花采样后，相关着色器的贴图采样数量会减少；实际整机 FPS 改善需实测，不能从此直接保证。

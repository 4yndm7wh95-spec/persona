# 两个 Claude 会话协作规则（草案，2026-11-09，待用户确认）

用户同时用两个 Claude 账号（两个会话）做这个仓库，活儿会在两边之间来回交接。下面的规则用来避免两边改出冲突、重复定义、互相覆盖。

## 1. 分支

- 两个会话各有一条自己的工作分支（会话只能推自己被指定的分支）：
  - A：`claude/epic-archimedes-m9an69`
  - B：`claude/beautiful-keller-4lsbk4`
- **开工第一步**：`git fetch origin`，把对方分支合并进自己的分支（能 fast-forward 就 fast-forward），合并完先跑类型检查和预览，确认能编译、能渲染，再开始做新东西。
- **收工最后一步**：提交、推送，更新交接文档（见第 3 条）。工作区必须干净。
- 合并时不要无脑用 `-X theirs` / `-X ours`。逐个看冲突，两边都加了同一个东西时只留一份（这次就是两边都加了 `SinfulPierce`、云着色器的 `mask_r`，合并后编译不过）。

## 2. 同一时间只有一个会话在改同一块

- 用户交接时说清楚「接下来由哪个会话做什么」。另一个会话在这段时间里**不碰那一块**（比如华丽收场的 `SinfulShell.cs` / `SatanaelPuppet.cs` / 它的音效）。
- 真要两边同时干活，就按文件 / 功能分开（比如一个做华丽收场，另一个做防御特效），不要同时改同一个文件。

## 3. 交接文档

- **只用一份**：`docs/HANDOFF.md`，最新的写在最上面，每次交接追加一节，不另起新文件。
- 每节写：日期、哪个会话、分支和最新提交号、做完了什么、**没做完 / 待办**（写清楚原因和建议做法）、**用户这次做的决定**、需要用户确认的事。
- 接手的会话先读最新一节，再看 `git log` 对上提交。

## 4. 用户决定的记录

- `docs/HANDOFF.md` 末尾维护一份「用户决定」清单（日期 + 一句话），比如「受击音只放一次」「不做时停」「Joker 转枪声去掉」。
- 改东西前先查这份清单，不要把用户否掉的方案又做回来。两边的决定矛盾时，以日期新的为准；拿不准就问用户。

## 5. 命名和定义：先查再加

- 加新的音效名、着色器 uniform、常量、方法之前，先 `grep` 一下有没有同名或同功能的东西。**同一个功能只留一套实现**：已经有了就在原来的上面改，不要再写一套平行的（这次两边各写了一套场景遮罩）。
- 一个功能有两版待用户挑选时，用不同的名字并存（例如 `sinful_pierce_b`），用户定了以后删掉没选的那版。

## 6. 生成的素材（音效、贴图、骨骼）

- 脚本是源头：每个音效 / 素材都要能用 `tools/` 里的脚本重新生成，文件头写清楚输出什么。
- **一个脚本只写它自己的那几个文件**。跑完先 `git status` 看看，只提交本次要改的输出；顺带被重写了的其他文件（ogg 编码每次结果不完全一样）要还原。
- 改了骨骼（`build_rig_p5.py`）要跑 `stage_p5.py`，把 `art/p5/rig/` 和 `p5mod/pck_stage/` 一起提交。

## 7. Codex 和版本号

- Codex 同一时间只跑一个任务。任务单放 `docs/codex/`，文件名里写清楚功能；在交接文档里写明「已发给 Codex、等推送」的任务，避免两边各发一份。
- 版本号（`P5Joker.json`、`ModEntry.cs`）只由准备让 Codex 打包的那个会话改，改了在交接文档里写明。

## 8. 提交说明

- 提交说明写清楚「用户要求了什么 / 改了什么」。代码注释里涉及用户意见的写日期，方便另一边理解为什么这么改。
